请帮我生成一个“可长期维护的旅行手册”网页，输出为一个可直接运行的单文件 `index.html`。必须使用原生 HTML + CSS + JavaScript，所有样式和脚本内嵌，不要拆分多文件，不依赖 React / Vue / Tailwind / 构建工具，不要包含部署说明。

这是一个长期自用的旅行计划网页，不是博客，不是营销页。它需要像“高质感旅行控制台 + 精细化行程手册”，既要有视觉设计感，也要能高频编辑和现场查看。页面语言为简体中文，网页本身支持用户本地长期修改。

一、数据与协作规则
- 这个 prompt 只定义网页生成规则与数据映射方式，不包含任何具体旅行方案内容
- 当我给你一整套旅行方案时，你需要严格根据我提供的最新方案生成或更新页面数据
- 当我后续补充酒店、票证、机票、火车、逐日安排、地图点位、费用或检查项时，页面内容要据此同步更新
- 不要沿用旧行程中的具体城市、日期、酒店、票号、站点、预算或景点名称，除非我当前方案里明确再次提供
- 当我让你修改网页时，先更新本地代码，并同步更新 GitHub 仓库代码
- 除非我明确发出“部署”指令，否则不要重新发布 GitHub Pages
- 当我明确要求部署时，再基于 GitHub 仓库的最新代码发布到 GitHub Pages

二、基础要求
- 单文件 `index.html`
- 原生 HTML / CSS / JS
- 桌面端和移动端都要可用
- 打开页面即可直接使用
- 结构化数据保存在 `localStorage`
- 附件使用浏览器本地能力保存和读取，可用 IndexedDB / File API
- 刷新后，用户修改内容和排序结果仍然保留

三、页面模块
请构建以下一级模块：
1. Hero / 总览
2. VOUCHERS
3. TRANSIT
4. 费用与通票建议
5. CHECKS
6. TIMELINE
7. MAPVIEW
8. 左侧旅行书签目录

四、左侧旅行书签目录
- 页面左侧制作一个整体书签目录，始终可见
- 目录支持点击跳转到任意模块
- 目录项需要根据当前滚动位置自动高亮
- 目录过长时自身可以滚动，不要导致整个页面显示不完整
- 目录支持层级结构：
  - 一级：模块
  - 二级：城市标签、区域标签或行程分组标签
  - 三级：day 标签
- TIMELINE 的 day 要生成在城市或行程分组的次级标签下
- 导航入口中的地点内容，按日期合并到 MAPVIEW 每个 day 的最下方横向展示
- 快速筛选放到逐日安排下面，作为可收起的次级目录

五、总览 Hero 模块
- 页面顶部要有强视觉设计感，但不能造成过多留白
- 展示旅行日期、主标题、摘要、关键路径、核心提醒
- 顶部主路径只保留：
  - 机场名（中文）
  - 游览城市名
  - 车站名
- 不保留航站楼英文细节或冗余交通术语
- 总览模块中需要有以下卡片：
  - NOW FOCUS
  - TRIP ALERTS
  - CHECKS
  - MAPS
- 这些卡片全部改为上下排列，不能贴在右侧造成大块空缺
- NOW FOCUS 要和最新的逐日安排、时间节点联动同步
- TRIP ALERTS 展示临近的重要提醒
- CHECKS 展示出发前重点确认
- MAPS 展示地图模块入口

六、VOUCHERS 模块
- 用于展示酒店、住宿、机票、火车票、预订单等信息
- 每个小项目都支持：
  - 点击文本区域直接编辑
  - 删除
  - 拖拽排序
  - 上传附件
  - 打开附件
  - 替换附件
  - 重命名附件
- 上传附件入口直接放在每个小项目内部底部，不需要额外说明文字
- 上传、删除等按钮要简洁
- 新增按钮放在模块顶部
- 点击新增后，生成一个与当前结构一致但内容为空的新项目
- “机票行程”和“具体行程”也支持点击直接编辑
- 气泡栏 / 标签栏里的内容也支持编辑、删除、新增、拖拽排序

七、TRANSIT 模块
- 展示跨城交通、区间移动、日期、事件、状态、金额、建议
- 例如火车、机场转移、城际移动、酒店换乘
- 每个项目支持：
  - 点击文本直接编辑
  - 删除
  - 拖拽排序
  - 上传附件
  - 修改建议
  - 修改费用
- 新增按钮放模块顶部
- 新增后生成一个空白但结构完整的新条目
- “已出票”“金额”“待补”等状态信息，不要放在标题同行
- 这些状态应展示在日期和事件文字下方
- 费用区域要避免金额自己断行换行

八、CHECKS 模块
- 作为出发前确认清单
- 每个 check 支持：
  - 点击文本直接编辑
  - 删除
  - 拖拽排序
  - 新增
- 每个 check 下方支持备注输入
- 备注也支持修改和删除
- 删除按钮要更小、更轻，不要繁琐
- 整体交互风格与 VOUCHERS、TRANSIT 一致
- 修改不要依赖复杂弹窗，优先原位编辑

九、TIMELINE 模块
- 这是页面核心模块之一
- 按城市、区域或行程分组展示每日详细行程
- 每个分组下面展示多个 day
- day 标签不能使用 day0/day1/day2，而要使用真实日期格式，与 MAPVIEW 保持一致
- TIMELINE 需要有统一“编辑”按钮，只有进入编辑模式后才显示新增、删除、排序、修改能力
- 支持：
  - 新增日期
  - 删除日期
  - 调整日期顺序
  - 编辑日期标题与所属分组
- 新增日期时：
  - 只有在“全部”视图下显示新增入口
  - 需要能选择该日期属于哪个日程项目 / 城市 / 分组
  - 需要手动指定具体日期
  - 新增后自动生成新的 day 标签，加入对应分组下，并位于所有 day 标签后
- 排序后：
  - 更新 day 的展示顺序
  - 保持 day 编排和日期呈现合理连续
  - 联动 MAPVIEW 的 day 及顺序同步变化
- 每个 day 下的事件列表支持：
  - 点击文本编辑
  - 新增事件
  - 删除事件
  - 拖拽排序
- 每条事件中的 meta、标签、气泡栏内容也支持：
  - 编辑
  - 删除
  - 新增
  - 拖拽排序
- 气泡栏右上侧增加删除按钮，同一行可增加新增按钮
- 其他可排序区域也尽量支持统一拖拽排序

十、MAPVIEW 模块
- 每一个 day 都要有对应地图卡片
- 地图上标出当天所有目的地
- 每个标点都显示顺序编号
- 地图视野自动适配，使全部标点能清晰展示，不要大量聚集重叠
- 地图尺寸自动调整到最适合当前点位分布的比例
- 每个 day 下方单独横向展示当天的导航入口
- MAPVIEW 也要有编辑模式
- 每个 day 的地点支持：
  - 新增
  - 删除
  - 修改
  - 拖拽排序
- 若 TIMELINE 中新增 / 删除 / 排序 day，MAPVIEW 需要自动同步
- 若地点顺序变化，对应地图标号顺序也同步更新
- 地图提供“打开当日 Google Maps 路线”按钮
- 如果能稳定实现，可尝试内嵌 Google Maps
- 若直接内嵌受限制，则优先实现：
  - 清晰的自绘地图 / SVG 点位图
  - 自动适配视野
  - 外链到 Google Maps

十一、附件功能
- VOUCHERS、TRANSIT、CHECKS、费用模块都要新增上传附件能力
- 支持一个或多个文件
- 支持打开查看
- 支持替换
- 支持删除
- 支持重命名
- 附件卡片尽量紧凑，不要过于占用页面高度

十二、排序与交互统一规范
- 所有可排序区域尽量支持拖拽排序，包括：
  - vouchers
  - transit
  - checks
  - timeline 的 day
  - timeline 的 event
  - map 点位
  - 标签 / chip / bubble
- 排序结果实时保存
- 编辑、排序、新增、删除尽量统一在“编辑模式”中出现
- 平时页面尽可能简洁，减少操作噪音
- 文本区域点击即可修改，不要让用户频繁点“编辑字段”按钮

十三、视觉设计要求
- 页面整体排版要进一步优化，尽量减少无效留白
- 每个模块下的标题字体不要换行
- 内容尽量紧凑，但不能难读
- 每个模块内部也要减少体积占用
- 风格要像精致旅行手册，不像通用管理后台
- 可以有：
  - 高级纸张感 / 卡片感
  - 温暖但克制的旅行色彩
  - 有节奏的留白
  - 精细边框与阴影
- 字体、标题、模块层级要有杂志感和设计感
- 桌面端采用左侧目录 + 右侧主内容
- 移动端自动改单栏

十四、内容映射要求
- 当我提供完整旅行方案时，请自动提取并结构化映射到：
  - 总览路径和关键信息
  - 凭证信息
  - 跨城交通
  - 费用与通票建议
  - 出发前确认事项
  - 逐日安排
  - 每日地图点位与导航入口
- 酒店、火车票、机票、景点、开放时间、票价、预算、换乘路径、备注都尽量结构化展示
- 若原始方案中有明显的阶段划分，例如“巴黎”“南法”“返程”“东京”“关西”等，应自动映射到 TIMELINE 和目录的分组层级
- 若原始方案中提供具体日期，TIMELINE 与 MAPVIEW 必须使用真实日期展示

十五、实现偏好
- 代码尽量清晰
- 使用语义化 HTML
- 使用 CSS 变量统一主题
- 适度使用 SVG / Canvas / 自绘地图增强视觉
- 所有模块都直接可渲染，不要留空壳
- 页面打开后即可直接浏览和编辑

十六、输出要求
- 只输出完整 `index.html`
- 不要解释
- 不要伪代码
- 不要补充部署部分
